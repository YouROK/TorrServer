# Правила Git

Документ описывает, как ведется история в проекте: сообщения коммитов,
ветки, теги, релизы. Правила переносимые: как перенести в другой проект -
в разделе 10.

## 1. Основное

1. Основная ветка - `silo`, она же дефолтная в удаленном репозитории.
   В любой момент собирается и работает. Недоделанное в нее не попадает.

2. История линейная. Merge-коммитов нет: ветка перед слиянием
   перебазируется, слияние - fast-forward, либо коммиты складываются в
   один (squash).

3. Один коммит - одно изменение с одной причиной. Переименование,
   форматирование и правка логики не смешиваются в одном коммите.

4. Коммит должен собираться и проходить тесты. Не собирается - не
   коммитится в общую ветку.

## 2. Сообщение коммита

1. Формат: `тип(область): описание`. Область опускается, если изменение
   общее: `ci: build and publish release on tags`.

2. Сообщение на английском. Это язык кода и логов, поэтому история
   читается без перевода. Исключение - проект, в котором код и логи на
   другом языке.

3. Заголовок отвечает на вопрос, что теперь делает код или система, а не
   что делал автор. Императив, строчная буква, без точки в конце, до 72
   символов, обычно 40-60.

4. Типы:

   - `feat` - новая возможность;
   - `fix` - исправление ошибки;
   - `refactor` - изменение кода без изменения поведения;
   - `perf` - ускорение или экономия ресурсов;
   - `style` - оформление: стили, форматирование, отступы;
   - `docs` - документация и комментарии;
   - `test` - тесты;
   - `build` - сборка, зависимости, скрипты;
   - `ci` - конвейер, релизы, проверки;
   - `chore` - обслуживание, не влияющее на код: версия, конфиги.

5. Область - подсистема или модуль, одно слово строчными латинскими
   буквами: `web`, `torrent`, `hls`, `user`, `plugin`, `admin`, `ffmpeg`,
   `ci`, `release`. Одно и то же место всегда пишется одной и той же
   областью.

6. Тело отделяется пустой строкой, пишется абзацами обычным текстом,
   перенос по 76 символам. Объясняет причину и следствие: что было не
   так, что изменилось, какие есть ограничения. Diff не пересказывает.

7. В заголовке и теле не пишутся маркеры списков, эмодзи, `WIP`, `fixed`,
   `update`, `changes`, даты, имена и ссылки на задачи.

8. Служебные строки в конце (`Closes #12`, `Co-authored-by:`) идут через
   пустую строку после тела, по одной на строку, только когда они нужны.

9. Плохо: `fix bug`, `update web`, `added watched marks and bulk toggle`.
   Хорошо:

   ```
   fix(torrent): merge re-added torrents instead of overwriting

   A repeated add of the same hash overwrote the user card with empty
   values: title, poster, category and added_at were reset and viewed
   marks were lost. Merge instead: a non-empty title, poster or category
   replaces the old one, while added_at and viewed marks are kept.
   ```

## 3. Ветки

1. Готовая работа коммитится в `silo`. Отдельная ветка нужна только под
   крупную работу, которую нельзя разбить на заканчивающиеся куски: тогда
   она сливается в `silo` по правилам раздела 1.2.

2. Имя ветки: `тип/краткое-имя` (`fix/hls-seek`, `feat/fuse`) или
   `тип/номер-задачи`.

3. Ветка живет до слияния и после него удаляется.

4. Долгоживущая ветка - только по договоренности. Она регулярно
   подтягивает основную, чтобы расхождение не росло.

## 4. Перезапись истории

1. Переписывать можно только свои непушенные коммиты.

2. Опубликованную общую ветку не переписываем никогда.

3. Свою опубликованную ветку - только `git push --force-with-lease`, и
   после предупреждения тех, кто мог ее забрать.

4. `git push --force` в основную ветку запрещен. `git reset --hard` на
   общих ветках не используется.

## 5. Теги и релизы

1. Тег - это выпущенная версия. Он ставится на коммит, в котором версия в
   коде совпадает с тегом.

2. Версия поднимается отдельным коммитом `chore(release): 1.2.3` перед
   тегом.

3. Тег аннотированный: `git tag -a 1.2.3 -m "1.2.3"`, затем
   `git push origin 1.2.3`.

4. Тег на другой коммит не переносится. Ошибка в релизе исправляется
   новым тегом.

5. Релиз собирается из тега автоматически. Бинарники руками не
   собираются и в репозиторий не кладутся.

## 6. Что не попадает в репозиторий

1. Результаты сборки и кеши: `dist/`, `build/`, `bin/`, `.gocache/`,
   `node_modules/`.

2. Настройки редактора и локальные файлы: `.idea/`, `.vscode/`, личные
   скрипты, заметки.

3. Логи, дампы, базы, тестовые медиафайлы большого размера.

4. Секреты: ключи, токены, пароли, сертификаты, `.env`.

5. `.gitignore` пополняется сразу, как только мусор появился, а не после
   того, как он попал в коммит.

6. Секрет попал в коммит - ключ отзывается и выпускается новый, история
   чистится через `git filter-repo`. Удаление новым коммитом не помогает:
   старое значение остается в истории.

## 7. Перед коммитом

1. `git status` и `git diff` просматриваются целиком. `git add .` вслепую
   не используется, лучше `git add -p`.

2. Проверяется, что в коммит не попали чужие правки, отладочный код и
   недописанные места.

3. Проверяется сборка и тесты.

4. Диф отдельно просматривается на секреты и на большие файлы.

## 8. Откат

1. Ошибка в опубликованном коммите - `git revert`. История не
   переписывается.

2. Ошибка в непушенном коммите - `git commit --amend` или `git rebase -i`.

## 9. Проверка формата

Формат заголовка проверяется хуком, чтобы правило не держалось на памяти.
Хук лежит в репозитории и подключается один раз:

```sh
mkdir -p .githooks
cat > .githooks/commit-msg <<'EOF'
#!/bin/sh
# Проверяет заголовок коммита: тип(область): описание.
subject=$(sed -n '1p' "$1")
case "$subject" in
  "Merge "*|"Revert "*|"fixup! "*|"squash! "*) exit 0 ;;
esac
types='feat|fix|refactor|perf|style|docs|test|build|ci|chore'
if ! printf '%s' "$subject" | grep -Eq "^($types)(\([a-z0-9-]+\))?: [a-z]"; then
  echo "commit-msg: заголовок не по формату" >&2
  echo "пример: fix(web): fit add torrent modal into the viewport" >&2
  exit 1
fi
if [ "${#subject}" -gt 72 ]; then
  echo "commit-msg: заголовок длиннее 72 символов" >&2
  exit 1
fi
if printf '%s' "$subject" | grep -q '\.$'; then
  echo "commit-msg: точка в конце заголовка" >&2
  exit 1
fi
EOF
chmod +x .githooks/commit-msg
git config core.hooksPath .githooks
```

## 10. Перенос в другой проект

1. Без изменений переносятся разделы 1, 3, 4, 6, 7, 8: это общие правила
   Git, а не особенности проекта.

2. Заменяются под проект: основная ветка, список типов (раздел 2.4),
   список областей (раздел 2.5), язык сообщений (раздел 2.2), схема
   версий и тегов (раздел 5).

3. Области лучше взять из структуры каталогов проекта: одна область - один
   каталог верхнего уровня или один модуль.

4. Список типов сокращать не стоит: лишний тип в списке дешевле, чем
   `misc` в истории.

5. Документ кладется в корень репозитория и упоминается в правилах
   проекта, чтобы новые участники находили его сразу.
